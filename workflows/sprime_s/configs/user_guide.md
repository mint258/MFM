# S′ 构象生成与 S 收敛测试指南（Codex）

Oct 12, 2026 · @Zixiao

本轮并行两个任务：A 在空闲 CPU 节点上为正式人口生成 UFF 力场构象数据集 S′；B 用现有 PM7 几何和 S 标签训练，判断当前数据规模下 1 个 epoch 是否足以收敛。两项都不依赖 WP5，可以和 WP5 同时进行。

## 通用规则

1. **原 LMDB 只读，不建新 LMDB。** 训练直接按记录索引读原 LMDB；S′ 结果写 parquet。
2. **不占用 compute-0-14 到 19**，这六台留给 WP5。CPU 任务用 `sinfo` 找其他空闲节点，尽量拉高并发；GPU 任务用之前 probe 训练用过的同类资源。
3. **人口与划分以 WP5 第 1 步的正式人口清单为准。** 如果尚未产出，按同一规则自行生成：放宽 I01、排除 4,900 条隔离记录、与 FULL 共享骨架键的 TRAIN 分子按连通分小移入 FULL。WP5 清单出来后逐条核对，不一致就报告。
4. **小文件规则同 WP5**：中间文件放节点本地 scratch，共享存储上只写少量大文件。
5. **发现问题记录并继续**，只有各任务列出的停止条件才暂停。未写明的训练参数沿用 `frozen_protocol.json`。

## 任务 A：用 UFF 生成 S′ 构象数据集

目标：给正式人口中的每个分子生成与 S 同样数量的力场构象。和 S 相比，只改变几何来源，分子、立体异构体、原子顺序都保持一致。

1. **输入分子图**
   - 以数据库中该分子的 SMILES 所表示的分子图为准，包括显式 H 和形式电荷。
   - 直接用原记录的原子和键构建 RDKit 分子，保证 S′ 的原子顺序与原记录一致，以便逐原子对比。构建后的分子须与数据库 SMILES 的规范形式（去立体）一致，不一致就标记。
2. **立体处理**
   - SMILES 已指定的手性和 E/Z 保留。
   - 未指定的立体中心和双键，按该分子最低能 PM7 构象的 3D 结构确定，保证 S′ 与 S 是同一个立体异构体。否则 ETKDG 会随机选立体，引入额外混杂。
   - 同一分子内立体签名矛盾的分子（手性 28,146 个、E/Z 8,108 个）也以最低能构象为准，并标注。
   - 每个分子记录立体来源（SMILES / PM7 几何）。
3. **构象生成**
   - ETKDGv3，随机种子由 molecule\_id 确定性派生。
   - 设该分子在 S 中有 N 个构象（最多 10），生成 3N 个候选。
   - 逐个用 UFF 优化，迭代上限取足够大（如 2,000），记录是否收敛。
   - 按重原子 RMSD 0.5 Å 去重，取能量最低的 N 个。不足 N 个就如实记录，不复制凑数。
4. **失败处理**
   - 嵌入失败先用随机初始坐标重试一次，仍失败记为 EMBED\_FAILED。
   - UFF 缺参数记为 UFF\_UNSUPPORTED。
   - 不换用其他力场，不删除分子。
5. **与 S 的几何对照**：每个 S′ 构象与该分子各 PM7 构象对齐后的最小重原子 RMSD；每个分子报告 S 的构象有多少被 S′ 覆盖到（RMSD < 0.5 Å）。
6. **输出（parquet，按 WP5 的五个文件组分片）**
   - 键为 `(molecule_id, sprime_conf_idx)`。
   - 字段：坐标（float64，原子顺序同原记录）、UFF 能量、收敛标记、迭代数、随机种子、立体来源、与最近 PM7 构象的 RMSD、状态。
7. **先试跑再全量**
   - 先按文件组分层抽 1 万个分子试跑，报告单分子耗时、各类失败率、RMSD 分布，并外推全量核时和存储。
   - 外推核时 < 5,000 且失败率 < 1%，直接跑全量；否则报告并等确认。
8. **验收**：每个分子都有状态，计数与人口清单闭合；随机抽 100 个分子用同一种子重跑，坐标一致。

## 任务 B：S 标签训练，判断 1 个 epoch 是否足以收敛

目标：在当前数据规模下（放宽人口的 TRAIN 约 1,110 万条记录），判断 S 预训练 1 个 epoch 是否足以收敛；同时实测训练吞吐，用于规划后续 8 组条件和数据规模曲线。

**设置**

1. **数据**：按正式人口清单中 TRAIN 记录的索引读取原 LMDB。验证用 FULL（含移入的泄漏分子）和 ROUTINE。**1 个 epoch 定义为遍历全部 TRAIN 记录一次**，同时报告折合的分子数。
2. **模型与标签**：用主架构及 `frozen_protocol.json` 的模型配置，只开 S 的三个任务（坐标去噪、遮蔽元素、键级）。三者用固定损失权重，不启用动态 balancer，记录权重取值。
3. **两组运行**（区分真收敛和学习率退火造成的“假收敛”）：
   - **B1**：学习率计划按 1 个 epoch 设计（warmup 后余弦衰减，在 epoch 1 结束时降到底），跑 2 个种子。
   - **B3**：其他设置相同，学习率计划按 3 个 epoch 设计，跑 1 个种子；在 0.25、0.5、1、2、3 个 epoch 处存 checkpoint。
4. **监控**（每固定步数记录一次）：
   - 三个任务在 TRAIN、FULL、ROUTINE 上的损失；
   - 去噪 RMSE，并和两个参照对比：带噪输入 0.141 Å、查表基线 0.042 Å（上次审计时模型只有 0.123 Å，不如查表基线）；
   - 遮蔽元素准确率、键级准确率、梯度范数；
   - 吞吐（记录/秒）、GPU 显存、数据加载等待时间占比。
5. **下游探针**：在 B1 的终点和 B3 的各个 checkpoint 上，冻结编码器做线性探针。
   - 用 `frozen_protocol.json` 指定的下游评估集；未指定就用 ESOL、Lipophilicity、BBBP 和 QM9 HOMO-LUMO gap 子集，scaffold 划分。
   - 下游分子的构象用 RDKit ETKDG + UFF 生成。
   - 报告下游分子与预训练人口在骨架 InChIKey 上的重叠数（只报告，不删除）。

**判定标准（预先定好）**

- **1 个 epoch 足够**：B1 终点在 FULL 上各项损失与 B3 在第 3 个 epoch 的相对差异 < 2%，并且下游探针差异小于 B1 两个种子之间的差异。
- **不足**：用 B3 的曲线估计需要多少个 epoch 才能让进一步增益 < 2%。
- **去噪单独判断**：如果 epoch 1 结束时去噪 RMSE 仍不低于查表基线 0.042 Å，单独作为问题报告。这说明先要查去噪头或噪声设置，而不是数据量问题。

**停止条件**：损失出现 NaN 或发散；实际读入的记录与清单不一致；去噪 RMSE 在训练超过 0.1 个 epoch 后仍不低于带噪输入的 0.141 Å。

## 交付与汇报

**任务 A**

- S′ parquet（按五个文件组分片）及 SHA 清单。
- 试跑报告：单分子耗时、失败率、全量外推。
- 全量闭合表：各状态计数、构象数不足 N 的分子数、立体来源分布。
- S′ 与 S 的几何差异汇总：RMSD 分布（按大小分层）、S 构象被 S′ 覆盖的比例。

**任务 B**

- 各项损失和指标随步数变化的曲线（B1 两个种子、B3 全程）。
- 判定结果：1 个 epoch 是否足够；不足时估计所需 epoch 数。
- 下游探针结果表（各 checkpoint × 各任务）。
- 吞吐、每个 epoch 的墙钟时间、GPU 类型与数量、数据加载是否成为瓶颈。
- checkpoint 与完整训练配置。

**总结报告第一页只放**：1 个 epoch 是否足够及依据；去噪头是否超过查表基线；单 epoch 训练时长；S′ 生成成功率和与 S 的几何差异；待用户决定的事项。

S′ 的训练、S/S′ 对比和数据规模曲线不在本轮范围内，等本轮结果出来后另行安排。
