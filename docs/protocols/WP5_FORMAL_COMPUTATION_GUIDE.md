# WP5 正式计算行动指南（Codex）

Oct 10, 2026 · @Zixiao

本轮在 compute-0-14 到 19 上一次性完成约 1,123 万条记录的 C/D/xTB 全构象标签计算，预计实际消耗约 3.8 万分配核时。结果只写 parquet 和原始输出归档，不建 LMDB；lmdb\_1 的字段格式在计算完成后另行讨论。

## 硬性规则

1. **原 LMDB 只读**，任何步骤都不得写入或修改原始数据和原 manifest。
2. **本轮不建任何 LMDB**（包括 lmdb\_1）。解析结果写 parquet，原始输出写归档容器（见第 4 步）。
3. **正式计算只用 compute-0-14 到 compute-0-19**，并把这六台节点用满。第 0 步的测试也在这六台上做。
4. **所有任务一次性提交**，不得跑完一轮再交下一轮。收尾任务也在同一时刻以依赖关系预先提交。
5. **单任务时限 48 h**，任何任务都不能被 Slurm 硬超时 kill。靠任务内的截止保护正常退出，剩余分子交给收尾任务。
6. **共享文件系统上不出现逐计算的小文件**。计算在节点本地 scratch 进行，共享存储上只写少量大文件。
7. **发现问题就记录并继续**。只有第 5 步列出的停止条件才暂停，暂停方式是“停止领取新分子、写 checkpoint、正常退出”，不是 scancel。
8. **不删除任何已有文件**（包括历史小文件），除非用户单独批准。本轮自己产生的临时文件除外。
9. 本文未写明的参数，一律沿用 pilot 冻结协议；需要偏离时先记录理由并报告。

## 第 0 步：提交前闸门

六道闸门全部通过才能进入第 3 步。任一道不通过，写明原因和备选方案后等用户确认。

1. **G1 分区时限**：用 `scontrol show partition` 确认所用分区的 MaxTime ≥ 48 h，并确认六台节点都在该分区内。如果不足 48 h，按实际上限减 15% 作为打包目标，并报告。
2. **G2 本地 scratch**：在六台节点上分别确认本地盘路径、可用容量、是否在作业结束后自动清理。要求每个槽位至少有一个分子批次的工作空间（以 pilot 最大分子的临时文件量的 10 倍为下限）。
3. **G3 存储与归档实测**：
   - 用 pilot 的全部原始输出，按计算类型（MOPAC 各任务、xTB 各任务）分别训练 zstd 字典，字典文件计 SHA 并随归档保存。
   - 实测“字典 zstd + 容器文件”下的两种保留策略：全量保留；普通成功只留最低构象、失败全留、另加 1% 随机审计样本。
   - 按本文配置（无 POLAR、ESP、Hessian）和正式人口外推两种策略的写回峰值，同时计入 parquet、日后导出的训练格式（float32，预留 400 GB）和临时余量。
   - **全量保留时峰值余量 ≥ 200 GB 就采用全量保留**，否则采用第二种策略。两种都不到 200 GB 就停下报告。
4. **G4 冻结**：固定并记录 SHA：正式人口清单（第 1 步产出）、标签登记表 v2、runner、parser、字典、打包清单、MOPAC 与 xTB 版本及全部关键词。parser 须包含本轮已验证的 D4 表解析修复。
5. **G5 parser 回归**：新 parser 重解析 pilot 全部 10,020 条记录的归档输出，除 POLAR、ESP、Hessian 外的每个字段与 pilot 结果逐位一致（或一致到字段记录的舍入精度）。不一致的字段逐一列出。
6. **G6 冒烟测试**：在 compute-0-14 到 19 上各跑一个短任务（每台约 20 个分子，覆盖五个文件组和大分子），走完整正式链路：本地 scratch、解析、归档、checkpoint、一次人为触发的截止退出与续跑。重点记录 compute-0-15 和 0-16 的内存峰值（上轮未实测）。

另外顺手做一项只读统计：配额显示该账户约有 2.8 亿个文件，按顶层目录统计文件数和字节数，交给用户。**不移动、不删除**。

## 第 1 步：正式人口与划分

产出一份正式人口清单（parquet）。每条记录含 record\_id、molecule\_id、源路径与 real\_index、payload SHA、文件组、新划分角色、全部 QC 标注。不改原 manifest。

1. **起点**：筛查报告的放宽保留集，11,236,754 条记录 / 1,220,956 个分子（`relaxed_quality_annotations.parquet` 中 `retained=true`）。
2. **排除隔离记录**：去掉 4,900 条 / 490 个分子（4,100 条外部测试集完整键 embargo + 800 条 QM7 组成 embargo），预期剩 11,231,854 条 / 1,220,466 个分子。保留它们的可追溯记录，但不进入计算。
3. **泄漏分子移入 FULL**：
   - 用重新识别的 14 位骨架加质子化字符作为键，建立“molecule\_id–键”二分图。一个分子的不同构象可能对应多个键，都要连上。
   - 取连通分量。凡是包含至少一个 FULL 分子的分量，其中所有 TRAIN 分子整体改为 FULL。以分子为最小单位，不按单条构象移动。
   - 预期移入约 1.3 万条记录（筛查 A3 的放宽骨架共享涉及 TRAIN 12,989 条），以实际连通分量结果为准。
   - ROUTINE 监控子集不变。移入的分子只进 FULL，不进 ROUTINE。
   - 移动后复核：TRAIN–FULL 在源完整键、重识别完整键、骨架键三种口径下的共享数都应为 0。
4. **QC 标注只标不删**：T01（含本轮放宽接受的完整键差异）、同一分子内立体签名矛盾（手性 28,146、E/Z 8,108 个分子）、S01、S02、H01、B01，以及说明层异常（42,088 + 2,263 条）。
5. **分配文件组**：按分子最大重原子数划入 ≤22 / 23–26 / 27–30 / 31–36 / >36 五组。
6. **闭合表**：给出各步前后的记录数与分子数、各角色（TRAIN/FULL/ROUTINE）计数、五组计数。各层必须完全闭合；不闭合即触发停止条件。

## 第 2 步：计算内容

每条记录（即每个构象）都在原 PM7 坐标上计算下表任务。坐标按原原子顺序导出（C5 已验证往返偏差 5×10⁻¹³ Å），不做任何优化。

| 任务 | 状态 | 说明 |
| --- | --- | --- |
| pm7\_B | 保留 | 中性单点及全部 B 类性质；**从关键词中去掉 POLAR** |
| pm7\_cation / pm7\_anion | 保留 | UHF 离子态单点，用于垂直 IP/EA 和 Fukui |
| pm7\_water / pm7\_octanol | 保留 | COSMO 溶剂化 |
| pm7\_ESP | **删除** | 失败样本重跑 0/200 恢复 |
| xtb\_singlepoint | 保留 | 电荷、Wiberg 键级、多极矩、轨道能、D4 |
| xtb\_vipea / xtb\_vfukui | 保留 | 垂直 IP/EA、Fukui |
| xtb\_ALPB\_water / xtb\_ALPB\_octanol | 保留 | ALPB 溶剂化 |
| xtb\_fod | 保留 | FOD |
| xtb\_perturbed\_gradient | 保留 | 扰动构象的能量与受力；扰动坐标一并保存，单独存放 |
| xtb\_hessian | **删除** | 本轮不算 Hessian 或 OHess |

其他要求：

- **关键词与版本**：除上表的删除项外，关键词、电子温度、溶剂参数、单次计算超时、随机扰动的种子规则全部沿用 pilot 冻结协议，并写进 G4 冻结清单。
- **能量标签**：P 组能量取本轮 pm7\_B 重算的生成焓。原 LMDB 存储的值另存为旧字段，并计算两者之差作为 Q02 标注。
- **D 组修订在同一流水线里完成**（CPU 开销可忽略，避免再扫一遍数据）：
  - 2D：删除 Kappa1–3，得到 20 个描述符；NumHAcceptors 按当前 RDKit 重算。
  - 3D：在原 PM7 坐标上计算 PMI1–3、PBF、分子体积、SASA 总量和逐原子 SASA。
  - 3D 描述符归入 D 组，不放进 P 组。
- **标签登记**：所有解析字段必须对应登记表 v2 的 ID，未登记字段为 0。推导量（如 Fukui、IP/EA、溶剂化能差）本轮照常解析保存，是否去冗余留到格式讨论时决定。
- **QC 只标注**：Q01 梯度范数、Q02 能量复现差、离子态自旋污染、各任务状态，全部逐条记录，不据此删除记录，缺失值不填零。

## 第 3 步：打包与一次性提交

**打包**

1. 用 C2 的耗时模型重新打包正式人口，去掉 POLAR、ESP、Hessian 的耗时，保留 p90 残差膨胀系数（1.71）和大尺寸外推。
2. 普通任务的打包目标为最长 lane **约 40 h**（上限 48 h）。一个任务只含同一文件组的分子，同一分子的全部构象在同一个任务里。
3. **重原子数 >75 的分子（约 2,950 个）单独成任务**，打包目标降到约 20 h。这类分子的单分子实际耗时最高可达预测的 6.4 倍。
4. 任务内按预测耗时从大到小排序，先算最耗时的分子。
5. 输出打包清单：任务数、每个任务的分子数与预测 lane 时长分布、总规划核时、在 29 槽上的排程 makespan。预测任一任务超过 46 h 即重新拆分。

**提交**

1. 按各节点槽位数（4/4/4/8/4/5）把任务分配到 compute-0-14 到 19，尽量让各节点预测总时长接近。
2. **每个作业只绑定一台节点**（`--nodelist=<单个节点>`）。不要在一个作业里写多节点的 `--nodelist`，那会要求同时占用全部列出的节点。
3. 每个作业：`--cpus-per-task=24`、`--mem=32G`、`--time=48:00:00`。
4. **全部主任务一次性提交**。同一时刻为每台节点预先提交一个收尾任务，带 `--dependency=afterany:<该节点全部主任务>`。收尾任务从共享的“待处理清单”中领取分子；清单为空就立即正常退出。
5. 收尾任务的领取用原子操作（如重命名或文件锁），保证同一分子不会被两个任务重复计算。收尾任务自己也遵守截止保护。如果收尾后仍有剩余，报告并等用户指示，不自动继续提交。
6. 提交后记录全部 job ID 与任务清单的对应关系，只管理本轮自己的作业，不动其他用户的任务。

## 第 4 步：运行时执行与归档

**单个分子的处理顺序**

1. 在节点本地 scratch 为该分子建临时目录，写入全部构象的 xyz。
2. 依次运行第 2 步的全部任务，单次计算超时沿用 pilot 设置。
3. 立即用冻结 parser 解析，追加到任务的内存缓冲。
4. 原始输出按 G3 确定的保留策略压缩后追加进归档容器。
5. 删除临时目录。一个分子全部完成才算“已完成”，写入 checkpoint。

**解析结果（parquet）**

- 每个任务、每个文件组写 zstd 压缩的 parquet，按登记表 v2 的字段组织，并按标签家族分表：基础几何、D 组 2D、D 组 3D、PM7 中性态、PM7 离子态、PM7 溶剂、xTB 各任务、扰动构象、QC。各表都以 record\_id 为键，可直接关联；数值保留 float64 原值。这些 parquet 是永久主存储，不是临时文件，完成后不得删除或覆盖。每条记录逐任务带状态（SUCCESS、CALCULATION\_FAILED、PROPERTY\_FAILED、TIMEOUT 等）。
- 定期落盘（例如每累积一定分子数或每 30 分钟）。先写临时文件再原子重命名，保证任意时刻中断都不会留下半个文件。

**原始输出归档**

- 归档是按任务的容器文件（带 blob 列的 parquet、SQLite 或单独的归档 LMDB 三选一，属于归档，不是 lmdb\_1）。主键为 `(record_id, calc_type)`，值为用对应字典 zstd 压缩的原始文本，另存状态、字典 ID 和压缩前 SHA256。
- 输入文件、完整关键词、软件版本始终保存，不论采用哪种保留策略。
- 共享存储上的文件总数应控制在几百到一两千个量级。

**截止保护（保证不被 kill）**

- 领取下一个分子前检查：已用时间 + 该分子预测耗时的 p99 估计 > 46 h，就停止领取。
- 等已在运行的分子完成，落盘 parquet 和归档，写 checkpoint，把未开始的分子写入待处理清单，正常退出（exit 0）。
- 已开始但未完成的分子在续跑时从头重算，不拼接半个分子的结果。

**重试规则**

- TIMEOUT、信号终止、节点故障等偶发失败：由收尾任务重试一次。
- 方法本身的失败（如 vipea、vfukui 的确定性失败）：只记录不重试。
- 失败只影响对应字段，不影响该记录其他任务的结果和它在人口中的地位。

## 第 5 步：监控、QC 与停止条件

**每日汇报**（一页，写在固定位置）

- 已完成分子数与记录数，按文件组和节点分列；预计完成时间。
- 各任务成功率与失败类型，和 pilot 对照。
- 已用核时与预测的对比；各任务实际/预测耗时比。
- 共享存储已用量、配额余量、共享存储上本轮文件数。
- 各节点内存峰值，开跑前几小时重点看 compute-0-15 和 0-16。

**运行中 QC**（只标注，不删除）

- Q01、Q02、自旋污染的分布和 pilot 对照，分位数明显偏离就在汇报中列出。
- 每个 parquet 落盘后校验：字段都在登记表内、数组长度与原子数一致、无 NaN 冒充成功值。

**停止条件**（触发后所有任务停止领取新分子、落盘、正常退出，然后报告等指示）

1. 任何写入原始数据或原 manifest 的行为。
2. 人口或划分计数不闭合。
3. 配额余量低于 300 GB。
4. 任一任务类型在已完成的前 5% 分子中的成功率比 pilot 低超过 2 个百分点。
5. 任何任务发生 OOM，或被 Slurm 硬超时终止。
6. 按已完成比例外推的总核时超过 5 万（完成 10% 后开始判断）。

其他问题一律记录并继续。

## 第 6 步：验收与交付

**验收条件**

1. 正式人口中每条记录在每个计算任务上都有明确状态，计数与第 1 步的人口清单完全闭合。
2. 所有 parquet 和归档容器都有 SHA 清单，能逐条按 `(record_id, calc_type)` 读回。
3. 随机抽 200 条记录在同一环境重算，与正式结果逐字段一致（或一致到字段记录的舍入精度）。
4. 落在 pilot 里的分子，结果与 pilot 一致；不一致的逐条列出。
5. 各标签分布、缺失率（按元素和大小）、QC 分布与 pilot 对照，不做阈值删除。
6. 本地 scratch 临时目录已清空；本轮共享存储上没有逐计算的小文件残留。

**交付物**

- 正式人口清单（含新划分角色与 QC 标注）与闭合表。
- 按文件组和任务组织的 parquet、原始输出归档容器、zstd 字典、SHA 清单。
- 冻结清单（G4）、打包清单、job ID 对照、每日汇报存档。
- 一份总结报告，第一页只放：完成率、各任务成功率、实际核时与墙钟、存储占用与余量、待用户决定的事项。
- G0 附带的账户文件数统计（只读）。

**之后的工作**：计算完成后不要直接写 LMDB，先由用户讨论 lmdb\_1 的字段格式，包括推导量是否单独存储、能量字段的命名与新旧值、lmdb\_1 大小预算是否从 600 GB 上调。格式定下来后再执行写回。
