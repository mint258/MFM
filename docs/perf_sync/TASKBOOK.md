# P 训练提速任务书 v1：去同步、减少 kernel、主线程减负

2026-11-17 · @Zixiao

状态：待执行。本书是用户 2026-11-17 给出的独立授权，由单独的 Codex 窗口执行，不改变主线《模型线任务书 P》以及侧线 p-followup、p-heads 的任何运行、配置和判定。

## 给执行者的首要规则（先读）

1. **不干扰主线。** 只用符合准入的空闲卡。不停止、不抢占、不修改任何在跑任务，包括主线第 3 轮、p-followup 的 C/D/B1、p-heads 的训练。主线需要新卡时，主线优先。所有代码改动都放在默认关闭的开关后面，不修改主线和各侧线已有的配置文件。
2. **只做短测试，绝不做完整训练。** 测速一律是 100 步预热 + 1000 步计时；短训练检查每条最多 1000 次优化更新。**不得启动任何 3M 级别的训练**，也不得启动超过 1000 次更新的任何训练。
3. **只要有提速的希望就直接试。** 本书列出的各项不需要先论证收益，实现、测速、记录结果即可。没有效果的项如实记"无提速"，然后继续下一项。
4. **不过度防御。** 只在两个位置验证：改动是否改变了数值（按下文的两类验收），以及采样顺序是否保持不变。其他检查一律不加，不做二次回读，不写收据。
5. **不做本书没有的任务。** 新想法在日报末尾记一行。**每完成一项，就把结果推送到 GitHub。**

## 背景与已有结论（直接引用，不重测）

- **PR6**（11-12）：剖析显示反向占 44%、前向 32%、损失 16%；CPU 从 4 核加到 16 核，吞吐只从 45.8 升到 47.8 样本/秒。同卡 MPS 并发不采用。
- **PR8**（11-14，已合并）：3090 上从 52.25 提到 71.60 样本/秒（1.37 倍）。三项改动是分组字段计算、关闭向量头重算、读进程准备输入并预取 4 批。最终剖析中，反向占 38.2%、主干编码 28.2%、预测头 10.5%、损失 6.6%、IPC 4.8%、主进程 CPU 输入 0.22%。等价性验收方法（噪声底容差）和工具都已存在。
- **PR10**（11-17）：TF32 和 BF16 在 B32 下都不比 FP32 快，所有配置下主进程 CPU 都在 99–101%。保留 FP32，**本书不再测精度**。
- **尚未确认的判断。** CPU 100% 不能证明 CPU 是瓶颈，因为 CUDA 默认用自旋等待同步。现有剖析只采样了 CPU 调用栈，没有 GPU 时间线。PR8 之后损失占比从 19.6% 降到 6.6%、主干从 4.6% 升到 28.2%，这很像"等待 GPU 的时间挪到了下一个同步点"。所以第一步先测量。
- **静态检查找到的每步同步候选**（以 S0 的实测为准）：

| 位置 | 内容 |
| --- | --- |
| `model/backbone.py` | 2 次 `to_dense_batch`，未传 `max_num_nodes` 和 `batch_size` |
| `phase1/v31_training.py` | B3 PMA 的 `to_dense_batch` |
| `model/v3_heads.py` forward | `require(bool(torch.isfinite(h0).all()))` 等约 5 个运行时检查和 `int(batch.max())`；每个成对字段再有 3 个 `bool((...).all())`（成对字段约 12 个） |
| `model/v31_grouped_heads.py`、`model/shared.py` | `int(batch.max())`、`batch_index.max().item()` |
| `phase1/p_recipe_training.py` 训练循环 | `clip_grad_norm_(error_if_nonfinite=True)`；`float(norm)`；每个家族一次 `float(value.detach())`（约 10 次）；`float(total.detach())`；每步写一行 CSV |

## 测量协议（全书共用）

- **基准配置**：主线第 3 轮的 `round3/M2.json`（A1 + B3 + B4，B32，FP32/TF32 关闭，14 个读进程），即当前主线实际使用的路径。只复制到 `configs/perf_sync/` 后修改，不改原文件。
- **权重**：随机初始化 seed 0，以及主线 B3 的 3M checkpoint。不加载正在训练的 checkpoint。
- **卡型**：5090、4090、3090 各取一张空闲卡，用 UUID 固定，同一项的基线和变体在同一张卡上连续测。某种卡型没有空闲卡时就跳过，记一行，不等待。A800 不测。
- **测速**：100 步预热 + 1000 步计时，记录样本/秒、主进程 CPU%、整卡平均功耗、CUDA 分配峰值。每项只测一次；测得的提速小于 3% 时，同卡再测一次，取两次的平均。
- **CPU 分配**：与主线相同，按需申请，不 exclusive。S7 另做核数扫描。

### 两类数值验收

**A 类：不应改变任何数值的改动**（S1、S5）。
- 在固定的 20 个 batch 上，用两组权重分别跑单步前反向，逐字段损失和完整梯度与基线**逐位一致**。
- 1000 个 batch 的分子/构象序列和 RNG 与基线逐批一致。可复用 PR8 的 `input_equivalence` 工具。
- 如果不能逐位一致，就退到 B 类验收，并记录原因。

**B 类：会改变浮点求和顺序的改动**（S2、S3、S4、S6）。
- **噪声底**：在 S0 中，用基线实现在同一张卡上对同样 20 个 batch 跑两遍，得到 ε_loss 和 ε_grad，每种卡型测一次。
- **单步门槛**：逐字段损失满足 |Δ| ≤ 10·ε_loss + 10·ε_loss·|loss|（绝对加相对）；整模型梯度的相对 L2 差 ≤ 10·ε_grad。与 PR8 相同。
- **短训练检查**（真实使用即验收）：从同一随机初始化、同一 seed 训练 1000 次更新，基线和变体各一次。要求两者都没有 NaN/Inf，并且最后 200 次更新的平均总损失满足 |差| ≤ 0.01 + 3% × 基线值。不训练更多步数，也不做下游评价。

**判定**：某项通过验收，且在至少 2 种卡型上提速 ≥ 3%，记为"有效"。只作为建议，是否合入主线由用户在两轮之间决定。

## 各项任务

除了写明的依赖，各项之间没有先后顺序：S1 之外的各项可以并行实现、并行测速。S0 是所有测速的基线来源，应当最先完成，但只有半天工作量。

### S0 测量（最先做，不训练）

在三种卡型上，用基准配置跑 100 步预热后，采集 100 步数据：
- **GPU 时间线**：`torch.profiler`，同时开 CPU 和 CUDA activity；nsys 可用时也可以用 nsys。
- **同步点定位**：开启 `torch.cuda.set_sync_debug_mode("warn")`，记录每一次同步的调用栈。

输出：
1. GPU 实际忙碌时间占每步墙钟时间的比例；
2. 每步 kernel 数；
3. 每步同步次数和每个同步点的代码位置（对照上面的候选表，注明哪些是实测出来的）；
4. 主线程花在发射 kernel 上的时间；
5. 每步 H2D 拷贝的次数和字节数；
6. 两类验收需要的噪声底 ε_loss、ε_grad。

结果写进 `docs/perf_sync/S0_PROFILE.md`，附原始 trace 的路径。trace 文件不进 Git。

### S1 去掉每步同步点（预计收益最大）

开关：`step_overhead.sync_free`，默认 false。

- **读进程预计算元数据**：在读进程里用 CPU 张量算出每个 batch 的分子数、每个分子的原子数、最大原子数、成对索引和 padding 布局，以 Python 整数或 CPU 张量的形式随 batch 传给主进程。
  - `to_dense_batch` 一律传入 `batch_size` 和 `max_num_nodes`。
  - `int(batch.max())` 和 `.item()` 一律改用这份元数据。
- **运行时检查移到数据管线**：`v3_heads.py` 等处 forward 里的 `require(bool(tensor...))` 检查，改为在读进程中对 CPU 张量做一次，即每个 batch 送上 GPU 之前检查一次。开关打开时，forward 中不再做这些检查；开关关闭时，代码保持原样。
- **训练循环**：
  - 各家族损失和总损失在 GPU 上累积，每 1000 次更新才取回 CPU 一次。这与现有 `TRAIN_1000_updates` 的记录频率一致，记录内容不变。
  - 每步的 CSV 行先缓存在 GPU 张量里，每 1000 步批量写一次。行数和每行的字段不变。
  - 每步要用的裁剪前梯度范数 `float(norm)`，按下面两条处理：
    - clip 校准窗口（6 万–15 万样本）内保持逐步取值，以保证 p99 计算不变；
    - 校准结束、阈值固定之后，`clipped` 计数改在 GPU 上累积。`error_if_nonfinite` 改成在 GPU 上做有限性检查，结果随每 1000 次更新的记录一起取回。如果出现非有限值，在这次取回时报错退出，行为与原来相同，只是最多延迟 1000 步发现。
- **验收**：A 类。输出必须逐位一致；采样序列一致；日志内容在相同的 1000 次更新边界上完全相同。

### S2 融合优化器和裁剪

开关：`step_overhead.fused_optimizer`。

- AdamW 用 `fused=True`；不支持时退到 `foreach=True`。梯度裁剪用 foreach 实现。
- 验收：B 类。

### S3 注意力改用 SDPA

开关：`step_overhead.sdpa`。

- `model/attention.py` 和 `model/v3_latent.py` 中手写的 softmax 注意力，改用 `torch.nn.functional.scaled_dot_product_attention`。距离偏置作为加性 `attn_mask` 传入，padding mask 合并进去。
- 只启用支持加性偏置的后端，例如 memory-efficient；不支持时允许回退 math 后端，并记录实际使用的后端。
- 验收：B 类。

### S4 torch.compile

开关：`step_overhead.compile`，取值为 `none`、`encoder`、`encoder_heads`。

- 编译主干的每个 Transformer 层（`dynamic=True`）；`encoder_heads` 同时编译预测头。
- 记录编译耗时和 1000 步内的重编译次数。重编译次数超过 20 时，对原子数这一维用 `mark_dynamic` 再试一次。仍然超过的话，记为无效并继续下一项。
- 验收：B 类。测速时预热必须在编译完成之后才开始计时。

### S5 数据传输

开关：`step_overhead.async_transfer`。

- 读进程到主进程的 batch 改用共享内存张量。主进程把它放进锁页内存，在独立的 CUDA stream 上用 `non_blocking=True` 提前一批拷到 GPU，用 event 与计算 stream 同步。
- 目标是 PR8 剖析中剩下的 4.8% IPC。
- 验收：A 类。

### S6 CUDA Graphs（依赖 S1）

开关：`step_overhead.cuda_graphs`。

- **启动条件**：S1 实现后，S0 方式复测显示每步同步次数为 0。不满足就记"不适用"并跳过，不为此修改其他项。
- 按原子总数、分子数、成对条目数把 batch 分到不超过 8 个固定大小的桶，补齐到桶的上限，每个桶捕获一次前向、反向和优化器步骤。
- 补齐的原子和条目必须被 mask 完全排除，包括 B4 正则里的批统计量和 PMA 的注意力。
- 验收：B 类，并额外检查一点：在不需要补齐的 batch 上，单步结果与不用图时逐位一致。
- 时间盒为 4 小时，超过就记 UNRESOLVED，继续其他项。

### S7 核数扫描（在 S1 和 S5 之后做）

- 用 S1、S5 之后的最佳组合，在 5090 上扫描 CPU 核数 4、8、16、24 和读进程数 7、14、20，各测一次 1000 步。
- 只在节点上实际空闲的核数范围内扫描，不申请 exclusive。
- 用来回答"去掉同步之后，加核数是否开始有用"。

### S8 累计组合

- 把所有判为"有效"的项一起打开，在三种卡型上各测一次。
- 做一次 B 类验收：如果组合里只有 A 类项，就做 A 类验收。
- 给出相对 PR8 基线的总提速倍数，以及新的剖析占比（S0 方法采 100 步）。

## 真正的停止条件（其余情况一律"日报记一行，继续"）

- 需要删除本任务自身 scratch 以外的任何文件；
- 需要改变标签、mask、归一化、采样、学习率等任何科学配置，或改变日志记录的内容和频率（S1 中写明的批量写出除外）；
- 需要启动超过 1000 次更新的训练，或任何完整训练；
- 需要付费服务器；
- 需要修改或停止任何在跑任务，或把任何开关接入主线、侧线的运行配置。

其余规则沿用：单项诊断或修复超过 4 小时，或连续失败 2 次，标记为 UNRESOLVED，该项记为无效，继续下一项；成本超过估计的 1.5 倍只报告；基础设施故障直接修复重跑；单元测试只覆盖新逻辑；合并前跑一次完整回归。

## 不做清单

- 不做任何 3M 或更长的训练，不做下游 R1/R3 评价，不做超过 1000 次更新的训练。
- 不再测精度（TF32/BF16），不测同卡多任务（MPS），不改 batch size。
- 不在本书列出的位置之外重构模型或数据管线。不改模型结构、参数名或 checkpoint 格式；旧 checkpoint 必须能照常加载。
- 不对已通过的项重复测速或重复验收。测速只按测量协议在提速 < 3% 时补测一次。
- 不为单元测试已覆盖的逻辑另做检查，不生成收据、哈希或审批记录。
- 不修改 `configs/p_recipe/` 和其他侧线的文件，不修改 `docs/paper/`。
- 不停止、抢占或修改任何在跑任务，不申请 exclusive。
