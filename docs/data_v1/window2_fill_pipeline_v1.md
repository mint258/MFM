# Future multi-part S-prime fill pipeline

The current producer waits for every molecule in a part via pool.map before submitting another part. This independent runtime supplies slow tasks from later closed D7 parts to the same pool while an earlier part is still running. Each complete part is published immediately, with rows reconstructed in its original metas order, original part number, original geometry flattening and the existing atomic checkpoint write. No running/unreturned molecule or incomplete part is marked closed. Existing closed checkpoint parts are skipped before any part/source materialization.

`PartQueue` bounds submitted futures to workers*4 and holds at most one part of unsent full task inputs. It does not pre-read all600 parts/F64 arrays and never truncates the original scientific work. Fast qualification/stubs are the already passed implementation. Slow tasks use the passed fill-only loader (full PM7 pointers/formal rows and full UFF rows/IDs; no unused HOF/prior). Every slow job calls the unchanged original safe_fill. Unreturned/failed futures propagate without publishing their incomplete part. Only metadata checkpoint/manifest parts are stably sorted by part; each data file retains original per-part meta/candidate order.

Per-molecule independence was confirmed from source only: original fill.seed_for uses the fixed MID-derived sprime-ETKDGv3-v1 seed; EmbedMultipleConfs receives explicit params.randomSeed and numThreads1 on every deterministic prefix call. Candidate order, fallback, lowest Native energy anchor, all Native graph checks, UFF tolerances, RMSD/N stop and per-MID IDs remain inside that unchanged worker. SCIENCE.worker_init sets threads/logging and does not initialize an order-dependent RNG; the current fill does not call SCIENCE.process/generate. No new Native QA or numerical comparison is added.

Finalizer consumes the fill parts by molecule ID/actual source refs and rejects duplicate MIDs; it does not depend on completion order. The existing tested D7 operational prepare wrapper permits only worker-count changes when reopening ready DB, so a32→64 CPU allocation resumes the same prepared inputs without DB reprojection/staging. Worker initializer calls original d7.initialize, then existing keep_source_map.install_native_reader with DATA_V1_COMPLETED_SOURCE_CACHE_PLAN. That only redirects physical input reads; its already passed map test is not repeated. For node20 Root can use the closed11-source cache plan at control/window2_20261105/native_cache_closed_plan.json.

Root alone makes the future closed-part/idle handoff, prepares the resource/plan and submits. This implementation does not signal or submit anything. The new actual parent runs exactly one new in-memory scheduling/commit/resume test, then the producer:

    python -B -m unittest workflows.data_v1_final.conformers.window2_fill_pipeline_v1.test_v1
    python -B -m workflows.data_v1_final.conformers.window2_fill_pipeline_v1.run --plan ROOT_SELECTED_FILL_PLAN

The fixture compares prior runtime values with out-of-order future completion, proves a later part commits while an earlier task remains pending, checks original state/new-geometry order, stable atomic checkpoint metadata and resume skipping. It reads no real source data and performs no Native calculation, benchmark or independent QA. All production data/log/checkpoint paths remain external and exactly those in the existing plan.
