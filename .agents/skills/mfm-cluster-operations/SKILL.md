# 集群管理

本 skill 是摘要。具体命令和完整历史见全局技能 `huagong_hpc_requirement` 和当前分支 AGENTS.md（最上面的条目最新）；调度参数见 p-recipe 分支 `configs/p_recipe/scheduling.json`，提交入口 `tools/p_recipe/launch_plan.py --plan <plan.json>`，混合调度说明 `docs/p_recipe/HYBRID_SCHEDULING.md`。

## 1. 服务器与环境

- 开发服务器：`zixiao@202.38.247.57:22`，项目根 `/share/home/zixiao/descriptor_analysis`；Windows 侧 `X:\` 是它的实时 SSHFS 视图。服务器上的编辑走 `X:\`，不改本地 OneDrive 副本。先确认 `X:\` 可用和基于密钥的 `ssh descriptor-analysis-remote` 可用。
- Linux 命令通过 SSH 在计算节点上执行；不用本地 Windows 解释器跑服务器脚本；科学计算不在登录节点做。
- 学校付费服务器只用于用户明确批准的正式预训练，不用于开发或测试。使用付费服务器是停止条件。
- 凭据只用已有密钥或环境变量，不进仓库。

## 2. 节点分组

| 组 | 节点 | 用途 |
| --- | --- | --- |
| 小 GPU 组 | compute-0-0 ~ 0-7（主要 3090） | 预算 ≤3M 的运行：筛选臂和它们的 seed1、过拟合等短测试、读出评估、基线推断 |
| 大 GPU 组 | compute-0-20、0-22 | 预算 >3M 的运行（9M 确认、正式规模），组内 5090 > 4090 > 3090 |
| CPU 节点 | compute-0-8 ~ 0-19 | 所有不用 GPU 的工作：标签计算（PM7、xTB、UFF、RDKit）、预处理和打包、参数拟合、统计和 bootstrap、传统 ML、环境搭建、下载安装、CPU 测试、源码检查 |
| 禁用 | compute-0-21 | 不提交新计算 |

- 优先组没有合规空卡时，**直接用另一组的空卡**，不排队干等。
- 不占 GPU 节点的 CPU 做纯 CPU 工作；GPU 任务在 GPU 节点上只申请自身数据加载需要的 CPU。
- **短 CPU 任务直接 SSH**（2026-11-26，全文见 `docs/interfaces/SCHEDULING_RULE_20261126.md`）：CPU ≤ 16 且预计 ≤ 4 小时的任务，选 CPU 节点上实测空闲核足够的节点，`setsid nohup taskset -c … timeout …` 直接运行并记录 PID/退出码/CPU 时间，不 sbatch 排队；超 4 小时但能按游标切段的切成 ≤ 4 小时段。只有大批量数据集生成或 CPU > 16 才 sbatch 排队，不退到 GPU 节点；排队不是停止条件。
- Alpha 集群同理，只用没有 GPU 的主机。
- 节点实际属于哪个分区以现场 `sinfo` 为准（例：compute-0-2 曾只在 cpu 分区）。

## 3. GPU 准入

- 0~7：gpu 分区普通 sbatch。提交前按目标 GPU 的 UUID 核实没有被占用，并且有足够可分配 CPU。
- 20/22：混合调度。可分配 CPU 足够且显存合规时直接 sbatch；CPU 不足但目标卡显存占用 ≤30% 且剩余显存够本任务时，SSH 先跑，同时提交同一任务的 sbatch 接管作业。显存未知或不够、节点 DRAIN/DOWN 时不启动。
- 当前 Slurm 没有 GPU GRES，普通 sbatch 不能独占显卡，所以每次都要按 UUID 核实实际占用。
- 不使用 `--exclusive`；只申请实际需要的 CPU（P 训练是 workers + 2，现为 14 + 2 = 16）。
- 一张卡一个实验。只为已就绪的注册任务补位，不为填空卡提前启动仍有科学依赖的臂。
- 线之间抢卡时按用户写定的优先顺序（例：提速线拿到卡前优先；之后配方线 > 侧线；主线需要新卡时主线优先）。

## 4. 断点与接管

- 所有新启动的 P 训练都配 `handoff_request` / `handoff_ack`。
- 接管作业排到后，请求原训练在下一次完整优化器更新结束时保存完整状态并退出：模型、优化器、样本 / 更新计数、学习率位置、采样 RNG、Torch CPU/CUDA RNG、统计窗口。
- 保存先写临时文件，关闭并同步后原子发布最终 `.pt`，最后写完成回执；接管方确认回执、原进程已退出、自有 GPU 锁已释放后才在新 job ID 下恢复。不读不完整的断点，不双跑。
- 台账记录原运行与续训关系、回退量；GPU 成本扣除两种句柄重叠的时间。
- 已知教训：协调程序曾在旧保存函数写完前终止原进程，导致断点损坏、损失约 2 GPU 小时。所以只能用上述原子发布协议迁移。

## 5. 在跑任务的连续性

- 没有用户对某条运行的明确停止指令，就**不停、不迁移、不重启在跑的训练**；规则更新和小的配方改动只对新提交生效。
- 只处理自有进程。对进程操作前核对 UID、PID、启动时间、命令和所属作业；不按名称批量处理；不动其他用户的进程和其他线的作业。
- OOM 等可修复的执行问题按任务书处理并记录每次尝试的实际设置和真实退出状态。

## 6. 磁盘、inode 与配额

- 任何大文件传输、缓存、解压前，在实际目标节点用 `findmnt -T`、`df -B1`、`df -Pi` 查目标文件系统的可用字节和 inode；`/tmp`、`/var/tmp` 可能和根分区及 Slurm spool 共盘。
- 估算新增峰值（源文件、临时文件、新旧并存、partial 文件、所有窗口同盘的计划写入），跨窗口协调预留，不重复预算同一份空闲空间。
- 根分区至少保留 max(10 GiB, 总容量 10%)；账户 quota 按现行余量规则。余量不足或查不清时不开始，改用核实过的共享盘、减小缓存或分批。
- 运行期间持续监控，在触及预留前停止新增写入并保留可续传状态。不自动删除用途不明的文件，不改管理员目录。
- 已核实事故：一次复制约 29 GB 到某节点 `/tmp` 导致该节点 Slurm spool 写满、节点进入 drain。

## 7. 轮询、记录与成本

- 训练或排队时每 1800 秒查一次作业和可用 GPU；发现有已就绪任务而某张卡空着，就补上。
- 记录真实 job ID 或原生 PID / start_ticks / 退出码，不伪造 Slurm 身份；区分"已提交、在跑、部分成功、科学验收、归档完成"。
- 每轮完成后日报按卡型各报一行实测样本/秒和整卡平均功耗。
- 每周一次成本账，基于真实 Slurm 记录。成本超过估计 1.5 倍只报告，继续。
- 正式训练用持久 W&B（离线后同步）；W&B 同步和记账问题不阻塞科学主线。
